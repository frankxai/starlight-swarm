# Operation authority v1

Status: isolated authority primitive; **not wired to a runner or production activation**.

This slice closes one part of [runtime activation authority issue #15](https://github.com/frankxai/starlight-swarm/issues/15): a trusted service can convert two signed, operation-bound approvals into a durable reservation, consume it, issue one short-lived `leased-not-started` lease, redeem its separately bound credential into `start-authorized-not-observed`, accept one authenticated runner/channel claim as `runner-claimed-not-started`, renew that claim with a rotating authenticated heartbeat credential, record one server-attested process start as `runner-start-observed`, settle a fenced `never-started` or `process-terminal` runtime outcome, and append authenticated provider-usage evidence without releasing budget. Every receipt remains explicitly undispatched. Start, outcome and usage observations prove only their bound facts; they do not prove workload effects, success, model calls, repository changes, customer outcomes or reconciled spend.

## Trust boundary

`OperationAuthority` verifies the signed approval and budget receipts. `PostgresOperationAuthorityStore` is the concurrency and freshness boundary. In one transaction it verifies:

- the operation, exact target and parameter digest, external effect, maker/checker call and runtime lineage are bound by one SHA-256 digest;
- the operation digest was registered by the server-owned preparation path;
- neither receipt, issuer, key, operation nor effect was revoked;
- server-owned host evidence is fresh, ready, access-reviewed, secret-ready and has capacity;
- the host and approval permit every requested capability;
- the signed per-receipt budget matches the immutable durable registry entry and has remaining capacity;
- exactly one trusted, immutable `policy` window and one `daily` USD window cover database wall time and the full reservation lifetime;
- the requested cost fits both aggregate windows, even when other receipt IDs share the same budget policy;
- neither the operation ID nor external effect ID has received a previous reservation.

The reservation transaction reserves cost and a host slot, inserts the reservation, and appends an audit event. It returns separate high-entropy consume and cancel tokens once; only their SHA-256 digests are persisted, and the plaintext tokens are excluded from audit records. A denial is also appended. Prepared-operation cancellation is durable and audited. Admission, consumption, revocation and cancellation take the same database control lock and use database wall time for terminal decisions.

Budget-window registration uses the same authority lock. Each window has an opaque ID, budget policy, `policy` or `daily` kind, explicit UTC bounds, USD ceiling and reserved amount. Exact registration replay returns an idempotent typed success; changed or overlapping same-kind windows return a typed refusal and commit a denial audit event. Admission records one hold against each selected window. Bounds are supplied by the trusted policy layer rather than deriving a local calendar day in PostgreSQL, so 23- and 25-hour daylight-saving days remain representable.

Consumption presents its token and the exact operation, effect, binding and execution identity. It also precommits a separate, caller-generated lease-claim secret. Only that secret's SHA-256 digest is persisted and audited; the consume credential cannot be promoted into a start credential. Under the same lock, the store rechecks expiry, revocation, prepared-operation state, trusted-host evidence, the signed requested cost and the two durable aggregate holds. Cost and ledger equality remain PostgreSQL `NUMERIC` decisions rather than JavaScript floating-point comparisons. One conditional transition creates a durable, retry-stable `consumed-not-started` receipt. Existing consumed rows that lack a separately bound lease digest remain start-ineligible.

`leaseStart` presents the precommitted lease-claim secret, exact consumption and binding identity, a unique start-request ID and a bounded TTL. The store repeats the freshness, revocation, preparation, host, capability and aggregate-hold checks under the authority lock. One conditional transition issues a retry-stable `leased-not-started` receipt while the lease and current authority evidence remain valid. A different request ID, credential, identity, consumption, duration or binding fails closed. Expiry, revocation, prepared-operation cancellation and explicit cancellation terminalize an unredeemed lease and release its per-receipt budget, both aggregate holds and host slot exactly once. This is safe only because the lease remains unredeemed and no runner accepts it.

`redeemStartAuthorization` presents a distinct 32-byte-format bearer credential and the exact lease, worker identity and binding. The caller can no longer name its broker identity. In the same transaction, the store attests the directly authenticated PostgreSQL session role, its non-superuser/no-membership posture and its exact read/column-update/audit grants, then resolves the broker identity from fresh server-owned evidence keyed by that role and database. The resolved pair must equal the broker identity precommitted in the lease. Under the same database lock and advancing database wall clock, the store repeats expiry, revocation, preparation, host, capability and receipt/window ledger checks. A single conditional transition moves the declared cost from reserved to conservative committed USD and the host slot from reserved to authorized, returning a non-bearer receipt with `execution_observed: false`. Exact retries require the same fresh principal and current authority; invalid retries become `stop-requested` without releasing committed resources. Disabling or changing a principal proactively applies the same quarantine to its issued authority.

`claimRunnerStart` is an unwired online boundary. It presents the precommitted control credential, a unique claim-request ID, distinct precommitted heartbeat and start-observation credentials, and a separate one-use outcome credential, but runner identity is never accepted from request fields. An injected server-owned transport attestor derives runner, instance, runtime, host, channel binding, launch attempt and fencing generation. The default attestor always refuses, so this repository cannot claim a runner unless an embedding supplies authenticated session evidence. Under the same database lock, the store revalidates the broker principal, signed runner/runtime/host binding, preparation, revocations, fresh host evidence and committed budget ledgers. One conditional transition persists only credential digests and creates `runner-claimed-not-started`; exact retries require the same request, credentials, principal, execution generation and channel. Drift after acceptance becomes `stop-requested` with committed resources retained. The claim expiry is bounded by the runner access review, evidence-age ceiling and signed operation timeout.

`acceptRunnerHeartbeat` renews a live `runner-claimed-not-started` or `runner-start-observed` claim without changing its execution-observation state. It derives the same runner, instance, runtime, host and channel from fresh server-owned transport evidence, re-attests the broker database session and repeats binding, preparation, revocation, host, capability and committed-ledger checks under the database authority lock. Each accepted sequence consumes the current heartbeat credential and atomically rotates to a distinct next digest. Every issued digest is retained in an append-only, globally unique heartbeat-token ledger, so an earlier credential can never become current again. A validated server-owned minimum interval (one second by default and never configurable below one second) both throttles new accepted sequences using PostgreSQL wall time and derives a hard sequence ceiling from the original fixed authority lifetime; exact latest retries remain idempotent, and throttle denials create no durable row an authenticated caller could amplify. The caller cannot choose the renewal lifetime: expiry is the minimum of fresh evidence age, access review, reservation, lease and signed operation timeout. Only the latest exact request is retry-idempotent; stale sequences, old credentials, request collisions, identity drift and stored receipt drift cannot extend authority. Heartbeat receipts remain `not-dispatched`; they report whether start was already observed and always report `workload_effect_observed: false`.

`observeRunnerStart` is a separate, unwired evidence boundary. The request presents only the one-use start-observation credential and exact claim binding. A second injected server-owned attestor must provide fresh evidence binding a globally unique process instance and evidence record to the exact reservation, claim, operation, effect, runner identity, runner instance, runtime, host and authenticated channel. The default attestor refuses. Under the same authority lock and PostgreSQL wall clock, the store revalidates principal posture, signed binding, chronology, claim expiry, preparation, revocations, host capability and committed ledgers. One conditional transition records `runner-start-observed`; exact retries require the same immutable process/evidence identity and timestamps plus a currently live access review, while replay drift or stale authority becomes `stop-requested` without releasing committed resources. The receipt remains `not-dispatched`, explicitly says `workload_effect_observed: false`, and grants no terminal, recovery or side-effect authority.

`settleRunnerOutcome` is a distinct, unwired recovery boundary. Its request presents the precommitted one-use outcome credential and exact claim binding; a separate default-deny server-owned supervisor attestor supplies either positive `never-started` evidence or `process-terminal` evidence. Both variants bind the exact launch attempt and fencing generation and must prove restart fencing, a closed launch queue and quiesced descendants. The terminal variant must also match the persisted start observation and process instance byte-for-byte. Missing start evidence is never treated as non-start evidence. Under the PostgreSQL authority lock, one conditional transition records an immutable outcome receipt. A matched process-terminal outcome releases exactly one authorized host slot; never-started evidence remains recorded but conservatively retains capacity because a delayed contradictory start record has no shared durable supervisor ordering yet. If such authenticated start evidence later arrives, the row becomes `stop-requested` with both facts retained and no resource release. Exact retries require fresh principal/evidence review and the same complete execution binding; competing outcomes, evidence reuse and binding drift fail closed. Both variants retain all committed receipt/window USD and budget holds because runtime terminality is not usage reconciliation. Receipts explicitly report `workload_effect_observed: false`, `actual_usage_reconciled: false`, `released_cost_usd: 0`, and whether remote stop was independently confirmed.

`recordRunnerUsageEvidence` is a separate, unwired accounting-evidence boundary, not settlement. The runner claim precommits an opaque provider correlation and a sixth, independently generated usage credential. After an authenticated outcome, a default-deny provider attestor may supply a signed provisional or final cumulative USD statement bound to the exact reservation, claim, outcome, execution generation, provider account, meter and correlation. Evidence costs use versioned fixed-scale decimal strings and PostgreSQL `NUMERIC`; sequences are monotonic, credentials rotate once, and provider event/evidence identifiers and all issued token digests remain globally replay-resistant. Provisional statements may advance to one final statement, never backwards. Overage and nonzero never-started statements are retained truthfully and emit a budget-breach audit event. No statement—provisional, final or over-budget—moves committed USD, releases a hold or claims actual-usage reconciliation. Receipts state `actual_usage_reconciled: false`, `budget_commitment_released: false` and `released_cost_usd: 0.000000`.

`assessOpenAIProviderEvidenceConformance` is a non-wired refusal orchestrator for the evidence an OpenAI embedding can currently observe. Server-owned dependencies must verify the untouched webhook body, endpoint binding and replay state and must read every Costs API page with an Admin API client while preserving raw response digests and decimal lexemes. The evaluator receives the raw webhook body and headers only long enough to call that verifier; it never digests, retains or emits the signature, webhook secret or Admin API key, and dependency errors are sanitized. Its bundle digest covers only canonicalized redacted attestations. The currently documented surface authenticates a `response.completed` event carrying a response ID, while the Costs API returns one-day aggregate buckets groupable by project, line item or API key. Even a complete, uniquely grouped bucket covering the signed event has no response subject, so the result hard-codes `per_operation_cost_authenticated: false`, `runner_usage_evidence_eligible: false`, `settlement_eligible: false`, `budget_commitment_released: false` and zero release. No `RunnerUsageEvidence` is synthesized and committed budget remains locked.

The usage-token mutation sub-lifecycle is now isolated behind two fixed-search-path, `SECURITY DEFINER` routines: the broker may initialize only its own sequence-zero credential and provider correlation, while a separate provider-verifier database identity may append evidence and rotate that credential. The broker role retains read-only visibility needed by the wider lifecycle, but has no direct `INSERT` on usage evidence or usage-token history, no direct `UPDATE` on the current usage token or provider correlation, and no execution grant on the append routine. The verifier has no authority-table, column, sequence, temporary-object, or unrelated routine authority. It can call only the append routine after an embedding has verified provider evidence. Both callers must present plaintext single-use credentials, which are hashed inside the transaction; caller-supplied digests cannot select another reservation. Each routine takes the global authority row lock and independently validates its input, authenticated database session, stored claim/outcome, a database-enforced binding checksum, principal state, revocations, preparation, execution generation, evidence chronology, sequence/finality, token lineage, global replay identifiers and conservative committed ledgers before mutation. Broker-principal evidence has one fixed five-minute freshness ceiling and runner/provider evidence one fixed one-minute ceiling in both the public store and database routines; callers cannot weaken either policy through configuration. Every accepted evidence row and audit event records the verifier database role, database name and verifier-contract digest, and exact retries or stream continuation must preserve that provenance. Provider-evidence v1 remains fixed at six fractional USD digits; v2 is a distinct, fixed twelve-digit contract stored as `NUMERIC(20,12)`. Existing v1 rows migrate exactly, each stream is pinned to one evidence version, and authorization, commitment and release values remain six-digit contracts. Neither evidence version settles usage or releases budget. Exact routine source digests, signatures, owner posture, fixed `search_path`, `SECURITY DEFINER`, and lack of `PUBLIC` execution are attested. Effective routine, relation, column and sequence grants in PostgreSQL system namespaces are compared with recorded initial privileges. PostgreSQL's built-in, initdb-assigned `information_schema` relations retain only their standard non-grantable `PUBLIC SELECT`; newly created relations cannot enter that baseline. Other non-default direct or `PUBLIC` authority fails closed. Runtime initialization creates no role and grants no permission; a human/infrastructure owner must provision the dedicated `NOLOGIN` routine owner and separate verifier identity from deterministic review artifacts.

The provider attestor is a normative trust boundary: an embedding must verify the provider signature over the canonical evidence body, enforce issuer/key allowlists and key revocation, bind `evidence_sha256` to that verified body, and return only server-owned evidence. This module deliberately does not parse a provider-specific signature format or ship any provider keys. Its default attestor refuses, and no production attestor is configured here.

`reconcileRunnerHeartbeatExpiry` is an explicit but unwired reconciliation boundary. It uses the same PostgreSQL lock and advancing database wall clock. A live, internally consistent claim remains unchanged; expired or corrupted liveness becomes `stop-requested` exactly once. Because no terminal/non-start evidence exists, reconciliation retains committed USD and authorized host capacity and records execution state as unknown. There is no sweeper or scheduler invoking it.

`authority-role-contract.ts` is the machine-readable least-privilege contract. It requires a direct-login, `NOINHERIT`, non-superuser broker role with no memberships, effective `CONNECT`/`TEMPORARY` but no current-database `CREATE`, public-schema `USAGE` but no `CREATE`, SELECT only on authority inputs, column UPDATE only on enumerated non-usage lifecycle and ledger columns, INSERT only on the remaining append-only heartbeat/audit relations, audit-sequence use, and EXECUTE only on the reviewed control-lock and usage-initialization routines. Temporary-object creation is tolerated defensively, while transactions and routines pin `search_path` so a temp object cannot shadow an authority relation. A second direct-login verifier role must have only database `CONNECT`, schema `USAGE`, and append-routine `EXECUTE`; it may not read or mutate authority relations. The generated SQL states database-grant prerequisites; attestation rejects authority inherited through `PUBLIC` and role membership in either direction. The routine-owner artifact requires a separate `NOLOGIN`, `NOINHERIT`, non-superuser owner with no schema/database creation authority or unrelated owned objects, including overloads. This change does not create a production role, grant a production permission, or configure a credential. A broker role-contract digest change quarantines previously active authority during migration rather than silently inheriting it. The authority migration creates the routines and revokes default `PUBLIC` execution; owner and caller provisioning remain explicit infrastructure gates.

HMAC secrets are server-side material. Callers receive signed receipts, never signing keys. Issuers and key IDs are explicitly allowlisted; rotation is enforced by revoking `key:<issuer>:<key_id>` before removing the key from the configured keyring.

## Queen session binding

The operation binding includes the full subordinate call identity expected by the bounded maker/checker Queen session:

- mission ID, call ID, role, actor ID, execution identity and identity-evidence reference;
- context digest, prompt SHA-256 and timeout;
- profile repository, commit, path and digest;
- policy, plan and pack digests plus compiler version;
- lane, workload, runtime and host IDs;
- requested operation, exact resource identifier, effect-parameters digest, capabilities, budget policy, cost and unique operation/effect IDs.

The integration contract was rechecked against current `frankxai/Starlight-Intelligence-System` head `5ea67efd685a38617a47a80408fa77cb3e5983a8`; the bounded one-maker/one-checker Queen session was introduced at `dfbb339727943c4fc3833c5ca90e471bb155ec17` and is unchanged by the intervening memory-only commits. Package version `8.3.0` alone is not evidence for either commit.

## Deliberate limits

- `src/swarm/runtime-adapters.ts` retains `activation_authority: trusted-server-internal-authority-not-implemented`.
- No runner, queue, scheduler, autonomous retry loop, external mutation, credential delivery path or deployment wiring is added.
- Budget enforcement reserves declared USD cost. The new evidence ledger can retain authenticated cumulative USD statements, but it does not yet settle invoices, refunds, actual spend, token units or foreign exchange, and it releases no commitment. Those require a separate reconciliation contract and spent ledger.
- The unsigned JSON lease and redemption receipts are persisted facts, not bearer or offline authority. Redemption requires both the secret and an attested PostgreSQL broker-service session whose server-owned evidence matches the lease.
- The claim API can consume an embedding's authenticated runner/channel session evidence, but this repository supplies no production transport attestor, role, connection pool, certificate, workload identity or credential. Its default behavior is refusal.
- There is no runner adapter, dispatch, workload-effect observation, usage reconciliation, kill-switch integration or external side effect. The repository can consume server-owned fenced terminal/non-start and provider-usage evidence, but supplies no production supervisor or provider attestor. The provider-adapter conformance fixture is deterministic test data, not deployed verification and not a credential or key. Heartbeat proves only channel presence; start proves only a process-start record; outcome settlement proves only the fenced runtime outcome; usage evidence proves only an authenticated accounting statement. Only a matched process-terminal outcome releases internal host capacity; never-started retains it pending shared supervisor ordering. The strongest later database boundary is a function-only role; the current exact column-grant contract still assumes arbitrary SQL cannot escape the reviewed authority module.
- The reviewed broker role no longer has direct usage-evidence, usage-token, current-token or provider-correlation mutation grants. It still has read-only usage-table access and wider direct lifecycle authority for claim, heartbeat, start and outcome transitions; isolating those remaining transitions behind dedicated routines is still a prerequisite for production activation.
- Consumption is an internal lifecycle claim, not the capability-broker or worker-dispatch layer tracked in other pull requests.
- Reservation/lease expiry reconciliation remains lazy. Runner-heartbeat expiry has an explicit reconciliation method, but there is no sweeper for abandoned claims and no automatic release of committed resources.
- Consumption and release re-derive each aggregate ledger from all active holds under the authority lock. Each active reservation must have exactly one policy and one daily hold matching its signed policy and cost. Corrupt, unfunded or missing attribution fails closed; a failed terminal transition is rolled back and receives a separate durable integrity-refusal audit attempt.
- Initialization upgrades earlier PR #24 schemas. It cancels non-consumable reservation-only rows, rows without aggregate attribution, and old leases that lack redemption/control bindings; earlier authorized rows without a database principal become `stop-requested` with committed resources retained. Partial attribution or ledger drift blocks migration. Operational migration ownership, rollout and deployment remain unauthorized.
- Committed USD is a conservative authorization amount, not measured usage, an invoice, actual provider spend, revenue or proof of execution. A timeout, cancellation request or loss of contact does not release it or claim remote termination.
- The embedded suite establishes functional contract behavior. CI also provisions an ephemeral PostgreSQL 17 service for concurrent consumption, lease, cancellation and revocation races; only a linked successful CI run is evidence that the real-PostgreSQL lane passed for a particular commit. Neither is evidence of production readiness.

## Authorized integration sequence

1. A trusted preparation service constructs and validates the exact operation binding.
2. The control plane registers its digest and signed receipt ceiling, then registers explicit, non-overlapping `policy` and `daily` USD windows for the binding's budget policy.
3. Server-owned probes write strictly validated host evidence.
4. The Queen session host passes the same binding and signed receipts to `OperationAuthority.admit` immediately before a maker or checker call. It must treat both returned tokens as secrets and never log or persist their plaintext.
5. A trusted internal authority generates a distinct lease-claim secret and submits it with the consume token and exact bound identity to `OperationAuthority.consume`. It must retain the plaintext only in its protected request context; the authority stores and returns only its digest.
6. That authority may claim one bounded `leased-not-started` row by presenting the lease secret, exact consumption ID, a unique start-request ID and TTL while precommitting distinct redemption/control secrets and broker identity metadata. The returned receipt is explicitly not dispatched.
7. A human/infrastructure owner provisions the reviewed broker role and private pool outside this code change. The control plane registers fresh broker-principal evidence for that exact role/database pair.
8. Only that directly authenticated, attested broker-service session may redeem the start credential. It must treat the result as `start-authorized-not-observed`, not running evidence.
9. An embedding may supply a server-owned transport attestor and present distinct heartbeat, start-observation and outcome credentials to accept one bound claim. It must treat `runner-claimed-not-started` as authenticated connection evidence, not execution evidence. This repository's default attestor refuses.
10. The same authenticated session may present one monotonic heartbeat request and a distinct next credential. Acceptance rotates the stored digest and extends only within server-owned authority ceilings. Expiry reconciliation requests stop but cannot claim remote termination or release resources.
11. A separate server-owned start-evidence attestor may bind one process-start record to the exact claim and authenticated channel. Acceptance records `runner-start-observed` but no workload effect or completion. This repository's default start attestor refuses.
12. A separate supervisor attestor may settle a positively fenced never-started or process-terminal outcome. A matched process-terminal outcome recovers one host slot; never-started retains capacity. Both retain committed spend.
13. A separate provider attestor and no-table-access verifier database session may append monotonic provisional or final usage statements using the claim's precommitted provider correlation and rotating usage credential. The broker can only initialize the stream through its dedicated routine; it cannot append evidence. Evidence is immutable and may report a breach, but releases no budget and is not reconciliation.
14. Do not connect this primitive to dispatch before actual-usage settlement, remote-stop exercises, effect-specific rollback/completion evidence, token-unit budgets, independent security review and the issue #15 adversarial evidence exist.
